# Современные утилиты: контракт кандидата SF5

Статус: реализованы в исходниках кандидата, выпуск и установка у потребителей ещё не подтверждены. Эта страница не утверждает, что классы уже доступны на опубликованном сайте документации.

## Табличное расположение

`display-table` задаёт только `display: table`. Не подключает рамки, отступы или оформление таблиц. Поддерживает обычные responsive-префиксы SF5: `sm:`, `md:`, `lg:`, `xl:`. Старый `table` сохраняется с прежним совмещённым поведением; это совместимость, а не рекомендуемый способ получить только display.

## Вложенные сетки

`grid-col-subgrid` и `grid-row-subgrid` используют дорожки родительской grid-сетки по соответствующей оси. Сами по себе не включают `display: grid` и не задают область, занимаемую дочерним элементом: их используют вместе с `grid` и нужным span/placement. Поддерживаются базовая форма и `sm:`, `md:`, `lg:`, `xl:`. Существующие числовые значения `grid-col-*`, `grid-row-*` и `none` не меняются.

## Перенос текста

Модуль `text-wrap/default` содержит конечный набор:

| Класс | CSS | Назначение |
| --- | --- | --- |
| `text-wrap` | `text-wrap: wrap` | Обычный визуальный перенос |
| `text-nowrap` | `text-wrap: nowrap` | Не переносить текст |
| `text-balance` | `text-wrap: balance` | Равномернее распределять короткие заголовки по строкам |
| `text-pretty` | `text-wrap: pretty` | Улучшать перенос основного текста, если браузер поддерживает этот режим |

Текстовые данные и копируемое содержимое не изменяются. Это не решение для длинного неразрывного слова и не замена `overflow-wrap`. В первом профиле эти четыре класса базовые: неподдерживаемые `hover:`/responsive-комбинации не генерируются автоматически. При отсутствии поддержки улучшенного алгоритма браузер сохраняет обычное поведение переноса; JS-полифилл не подключается.

## Видимая область браузера

| Высота | Ширина | Смысл |
| --- | --- | --- |
| `h-screen-small` | `w-screen-small` | Маленькая область (`svh`/`svw`), с учётом раскрытых панелей браузера |
| `h-screen-large` | `w-screen-large` | Большая область (`lvh`/`lvw`) |
| `h-screen-dynamic` | `w-screen-dynamic` | Текущая динамическая область (`dvh`/`dvw`) |

Поддерживаются базовая форма и обычные responsive-префиксы SF5. Утилиты ссылаются на системные `--sf-viewport-height-*` и `--sf-viewport-width-*`; физические значения определены в Core. В старом движке fallback — обычная область `vh`/`vw`. Это размер области браузера, не размер контейнера компонента.

Прежние `h-screen`, `w-screen` и дробные `screen-*` не меняют значения. Маленькая/большая/динамическая область не меняет правила mobile/desktop типографики и размеров контролов.

## Проверка поставки

Изолированный пример должен подключать Core и получать необходимые модули через Loader, без полного utility bundle. Проверяются точные классы и отрицательные образцы, базовые и поддерживаемые responsive-варианты, LTR/RTL и темы. Для subgrid нужна геометрия родительских/дочерних дорожек; для viewport — размеры при изменении окна; для `display-table` — отсутствие загрузки модуля оформления таблиц.

## Контейнерные условия

`query-container` объявляет inline-size контейнер. `query-container/sidebar` дополнительно задаёт имя `sidebar`. Контейнер не назначает себе ширину или оформление: это отдельная задача компоновки.

`cq-sm:flex-row` использует ширину ближайшего подходящего контейнера; `cq-sm/sidebar:flex-row` — ближайшего контейнера с именем `sidebar`. Пороги sm/md/lg/xl берутся из той же исходной шкалы SF5, что viewport-условия, но измеряют другую область. `sm:` по-прежнему относится к окну.

Первый профиль задан в `src/core/contracts/container-conditions.v1.json`: четыре порога, одно имя `sidebar`, выбранные display/flex/grid/gap/justify/align роли. Он не включает произвольные имена, CSS-значения или произведение state×viewport×container. Все условия компоновки поставляются одним конечным модулем `query-layout/default`, чтобы результат не зависел от порядка загрузки CSS. Объявления контейнеров находятся в отдельном небольшом модуле `query-container/default`.

При сборке владельцем Framework `scripts/generate-container-conditions.mjs` создаёт конфигурацию и точные правила Loader; `--check` обнаруживает устаревшие проекции. Потребитель использует готовые файлы и ничего не компилирует. Изменение профиля требует нового согласованного выпуска, а не добавления runtime-класса на странице.

Вложенный контейнер без имени не перехватывает условие к `sidebar`; вложенный контейнер с тем же именем перехватывает. Сам элемент-контейнер нельзя адаптировать запросом к собственной ширине: условные классы размещаются на потомках. При отсутствии поддержки container queries остаётся базовая компоновка; viewport-подмена и JS-полифилл не включаются.

## Совместимая загрузка column-gap

`col-gap-*` — каноническое имя класса. При автоматическом обнаружении Loader использует модуль `gap` соответствующего условия вместо двух одинаковых загрузок `gap` и `column-gap`. Старые CSS-файлы `column-gap/{default,sm,md,lg,xl}` остаются в поставке; прямые подключения и закреплённые production asset plans не переписываются.

Записи совместимости находятся в `src/core/contracts/utility-module-aliases.v1.json`. `npm run test:utility-aliases -- /absolute/path/to/ui-builder` компилирует оба исходных модуля выбранным Builder и проверяет все 60 классов: декларации, !important, порядок, условия, слои, зависимости, отсутствие дополнительных эффектов и циклов. Это обязательная проверка кандидата перед выпуском; одна лишь успешная сборка её не заменяет. Подключение проверки непосредственно в штатный Builder pipeline остаётся незавершённой частью интеграции кандидата.

Unit-тесты также проверяют безопасное поведение при неполном реестре и неизменность закреплённых production-планов. Browser-проверка должна показать ровно один запрос `gap` на условие, правильные computed styles после изменения ширины окна и отсутствие автоматически запрошенного `column-gap`. Здесь описан проверяемый кандидат, не уже опубликованный выпуск.
